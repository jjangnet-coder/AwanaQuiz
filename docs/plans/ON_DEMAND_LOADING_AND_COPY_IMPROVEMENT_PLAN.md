# [수정계획서] 문구 표준화 및 교실/교시 온디맨드(On-Demand) 경량 로딩 아키텍처 개편

## 1. 개요 및 요구사항
사용자 피드백을 바탕으로 UI 문구 전면 정비 및 가장 중요한 **네트워크/메모리 부하를 획기적으로 줄이는 온디맨드(On-Demand) 데이터 로딩 방식**으로 전면 개편합니다.

1. **하단 상태 문구 정비:** 불필요하게 기술적인 `⚡ 실시간 중앙 집계 모드 (로컬 캐시 없음)` 제거 및 직관적 표현으로 간소화
2. **연결 상태 문구 개선:** `연결 상태: 정상 (실시간 스프레드시트 연결됨)` ➔ `구글 스프레드시트 연결 정상` 등 깔끔하고 신뢰감 있는 문구로 정비
3. **대기 안내 문구 개선:** "상단에서 교실명과 교시를 선택하면..." ➔ 상단에 교실 드롭다운이 없으므로(게이트웨이로 고정됨) **`상단에서 <b>교시</b>를 선택하면 해당 교시의 선수 명단이 나타납니다.`** 로 정확하게 수정
4. **시스템 타이틀 변경:** `2026-2027 AWANA 성경퀴즈대회 점수 입력 시스템`
5. **직책 명칭 변경:** `기록관` ➔ `점수기록관` (입력 라벨, 게이트웨이 팝업, 알림 메시지 일괄 적용)
6. **★ 핵심 성능 개선 (온디맨드 데이터 로딩):**
   - 접속하자마자 1,376명 전원 명단과 전체 점수를 한꺼번에 받아오던 방식을 폐지.
   - **교실과 교시가 선택되었을 때, 해당 교실/교시에 해당하는 1개 조(약 10~20명) 단원 데이터만 백엔드에서 핀포인트로 가져오는 초경량 구조**로 전면 전환.

### B. 교실-교시 기반 온디맨드(On-Demand) 초경량 API 설계 (`Code.gs` & `index.html`)

#### 1) 기존 방식의 문제점
- 웹 앱 접속 시 1,376명의 인적 사항 + 18개 시트 전체 점수 데이터를 통째로 JSON 직렬화하여 전송.
- 모바일/태블릿 환경에서 첫 진입 로딩 지연 및 데이터 낭비 발생.

#### 2) 개편 방식 (2-Stage On-Demand Loading)
- **1단계: 초기 진입 시 (메타데이터 초경량 로드, 1KB 미만, 0.2초 컷)**
  - `doGet`에 파라미터가 없거나 `action=init`인 경우:
    - `settings` (교실별 접속 PIN 코드, 스피드 룰)
    - `timetable` (12개 교실 순환 시간표만 반환)
    - ➔ **1,376명 명단과 점수는 일체 로드하지 않음!**
    - 게이트웨이 로그인 및 교실 잠금, 교시 선택창 즉시 활성화.

- **2단계: 점수기록관이 교시를 선택했을 때 (실시간 온디맨드 로드, 1~2KB 미만)**
  - 교시 선택 시 `doGet(e)` 파라미터 전달 (한글 인코딩 깨짐을 원천 방지하기 위해 `encodeURIComponent` 적용):
    `?action=getStudents&room=${encodeURIComponent(CURRENT_ROOM)}&period=${CURRENT_PERIOD}`
  - **백엔드(Apps Script):**
    - `const room = decodeURIComponent(e.parameter.room || '').trim();` 로 안전하게 디코딩.
    - 해당 교실/교시에 배정된 핸드북과 조(team)를 시간표에서 파악.
    - **해당 조에 속한 학생들(약 10~20명)의 명단만 필터링하여 반환.**
    - `최종집계` 시트에서도 **오직 해당 학생들의 점수만 핀포인트로 조회**하여 반환.
  - **프론트엔드:**
    - 불과 0.2~0.3초 만에 해당 조 명단만 쏙 받아서 테이블을 즉시 렌더링.

- **3단계: 본부 필기 시스템(`hq.html`) 호환성 보장**
  - 본부 시스템은 전원 명단이 필요할 수 있으므로 `?all=1` 파라미터 지원으로 기존 호환성 100% 유지.
